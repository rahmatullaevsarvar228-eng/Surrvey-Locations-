# Места, где трактовка ТЗ требует решения

Правила принятия решений (раздел 4, M5, таблицы M3/M4) **не менялись**. Перенесённый движок даёт
те же результаты, что эталон (`tests/test_equivalence.py`). Ниже перечислено то, что ТЗ или эталонный движок не
определяют однозначно, и как это сделано в программе.

## A. Эталонный движок: найденные крайние случаи (не исправлялись — нужно ваше решение)

1. **Двойное списание по BHMS 11 после прекращения проекта.** Если проект прекращён до готовности, а после даты
   прекращения внесена новая оценка с `Yo'q`, движок одновременно возвращает `writeoff` (списание при прекращении)
   и `nas_criteria_writeoff` (п.18) на ту же сумму. В сумме получается списание 2 × капитализация.
   Инварианты эталона этот случай не ловят, потому что проверяют их по отдельности.
   *В программе:* в проводках, отчётах и вкладке «Qaror» списание по п.18 с датой ≥ даты прекращения не
   отражается (тест `test_no_double_writeoff_when_assessed_after_abandonment`). Сам движок не изменён.
   *Предложение:* в `evaluate()` учитывать только оценки до даты прекращения при поиске списаний по п.18.

2. **Списание по п.18 с датой после готовности актива.** Если оценка `Yo'q` датирована после акта приёмки,
   движок исключает списанную сумму из амортизируемой базы **с самого начала** амортизации. При этом
   `carrying_amount()` до первой строки графика ещё показывает полную сумму (`schedule` и `carrying_amount`
   расходятся в этом окне). В инвариантах эталона это не проверяется.
   *В программе:* проводка списания (Дт 9430 — Кт 0830) датируется датой готовности, тогда счета сходятся
   с графиком. Тождество «счета = балансовая стоимость» проверяется на всех проектах, кроме этого
   случая (в 1 500 случайных проектах он встретился 3 раза).
   *Вопрос:* после готовности п.18 по смыслу уже не применяется (актив списывается через обесценение или
   выбытие). Возможно, оценки после готовности стоит просто игнорировать.

3. **Одно событие обесценения на проект.** Движок поддерживает только `impairment_event` в виде одной пары
   (дата, сумма). Таблица `impairment_events` в ТЗ допускает несколько событий. *В программе:* одно событие на
   проект (UNIQUE в схеме), повторный ввод заменяет прежнее и пишется в журнал аудита.

## B. Трактовки, где ТЗ допускает варианты

4. **Счёт источника (кредит) для категорий без значения по умолчанию** (`legal_registration`, `selling`,
   `general_admin`, `training`, `other`). В M6 эти категории не указаны. По умолчанию стоит **6010**,
   пользователь может изменить счёт в «Sozlamalar». Это заглушка, которую нужно проверить.

5. **E2.** Понимается как *текущее* состояние: проект сейчас в `ishlanma`, статус ≠ `bajarilgan` непрерывно
   дольше N дней (отсчёт идёт с начала разработки или с последней потери статуса), и за это время есть хотя бы
   одна затрата по R6. Прошлые, уже закрытые периоды не показываются. Иначе базовый проект S2 (91 день с 01.04
   по 01.07.2024) навсегда оставался бы с E2.

6. **E3.** Засчитывается любая оценка с датой ≤ «начало разработки + 30 дней», в том числе сделанная раньше
   перехода в `ishlanma`. Нарушение остаётся в отчёте навсегда: это факт опоздания, а не текущее состояние.
   По этой причине E3 есть у базового проекта S2.

7. **E6** считается от первой оценки в непрерывной серии, где критерий = «Ekspert», по последней оценке
   на «сегодня». Для готовых и прекращённых проектов E6 не проверяется.

8. **E9.** Порог по умолчанию 0 сум, то есть показывается любая разница балансовой стоимости на «сегодня»
   (уровень «инфо»). В ТЗ значение по умолчанию не задано.

9. **E10.** «Завершён» понимается как «готов к использованию». Активность: затраты, оценки, дата начала
   разработки, дата начала проекта.

10. **E8** проверяется на уровне проекта (дата готовности есть, срок = 0). В движке предупреждение E8 появляется
    только если есть капитализированная сумма.

11. **Состав «НИОКР в расходах за период»** (BHMS 11 п.20, IAS 38.126). В сумму вошли расходы по R2–R6 и R8.
    Затраты по R1 (продажа, админ., обучение, прочее) показаны **отдельной строкой**, а не в сумме НИОКР:
    это не затраты на исследования и разработки.

12. **«Переведено в другие активы» (п.20).** Понимается как амортизация, отнесённая на стоимость других активов
    по п.17. Она попадает сюда, если в настройках дебет амортизации = 2010 или 2510. Перевод 0830 → 0490
    (готовность) показан отдельно как внутреннее перемещение. «Восстановлено» (п.19) в v1 всегда равно 0, так как
    восстановление по ТЗ делается только вручную и в движке не реализовано.

13. **Изменение допустимости категорий (M12)** реализовано как необязательное поле `Settings.included`. Значение
    по умолчанию `None` совпадает с таблицей M4, и результат движка тогда идентичен эталону.

14. **Проверки входных данных** в эталоне сделаны через `assert`. При запуске с `python -O` они отключаются,
    поэтому в программе они явно выбрасывают `AssertionError`. Поведение S17 сохранено.

## C. Уже отмечено в ТЗ как позиция автора (оставлено как есть)

* отсутствие K3 в BHMS 11;
* исключение `training` по BHMS 11 (можно включить в «Sozlamalar», изменение пишется в журнал аудита);
* подход IAS 38.53 (R2) применяется и к BHMS 11;
* счёт 0830 для собственных разработок;
* порог 50 БРВ (BHMS 7 п.6) не проверяется.

## D. Технические

* **Windows exe** нельзя собрать в Linux-контейнере. Сборка и проверка запуска без Python идут в GitHub Actions
  (`windows-latest`), локально проверен Linux-бинарь из того же spec-файла.
* Шрифт **Segoe UI** задан в стиле. На скриншотах, снятых в Linux, его нет, поэтому Qt подставил другой шрифт;
  на Windows интерфейс будет в Segoe UI.
